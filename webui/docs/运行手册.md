# DMR WebUI 运行手册

适用范围：`DMR_WebUI/webui` 子工程（交易内核、Web 控制台、替身交易所）。本手册覆盖上线、回滚、应急三种场景。
**目前（M2）只有替身环境（`DMR_ENV=standin`）可用**；涉及主网的步骤标了「M7 起」，现在不要做。
所有命令都在 `webui/` 目录下运行；Python 一律用本工程自己的解释器（`.venv-kernel/bin/python`、`.venv-console/bin/python`），
不要用 `DMR_WebUI/venv`，也不要运行旧入口与旧脚本。

下文 `var/` 指运行期目录（环境变量 `DMR_VAR_DIR`，缺省 `webui/var`）。三个进程、端口与日志见 `deploy/README.md`。

## 0. 速查

| 想做什么 | 命令 |
|---|---|
| 启动全部 | `deploy/dev_start.sh` |
| 看状态 | `deploy/dev_status.sh`；内核内部状态 `.venv-kernel/bin/python -m dmr_kernel.cli status` |
| 停止全部 | `deploy/dev_stop.sh` |
| 只停开仓（内核存活） | `.venv-kernel/bin/python -m dmr_kernel.cli stop` |
| 全部托管持仓平仓（内核存活） | `.venv-kernel/bin/python -m dmr_kernel.cli close-all` |
| 内核死了或卡死，要平仓 | `.venv-kernel/bin/python -m dmr_kernel.cli emergency close` |
| 上线清点 | `.venv-kernel/bin/python -m dmr_kernel.cli inventory` |
| 创建操作员 | `.venv-kernel/bin/python -m dmr_kernel.cli create-operator --username <名>` |
| 备份恢复演练 | `deploy/backup_drill.sh` |

退出码约定（命令行）：0 成功；1 内核拒绝了请求或本地文件有问题；2 用法或启动配置不对；3 连不上内核或没拿到完整的答复；130 被 Ctrl-C 打断。

## 1. 启动

```
deploy/dev_start.sh
```

按 替身交易所（18220）→ 内核（18200，经 `supervise.sh` 守护）→ 控制台（18210）的顺序启动，每个都等健康检查通过；已在运行的不重复启动。
退出码：0 全部健康；1 某个进程没起来（脚本已打印原因和日志末尾）；2 配置无效；**3 停用标记 `var/run/kernel.nosupervise` 存在**（见第 6 节：
先确认为什么有它，再删除它，再启动）。

启动后内核要做「重启恢复」（对账、补记、补保护）。恢复期间状态条显示「恢复中」，此时只允许停止、平掉此仓、一键全平，
不允许启动、切换、部分平仓。恢复完成前不要点启动。

端口被占用时脚本会拒绝启动并说明；正式端口是 18200（内核）、18210（控制台）、18220（替身交易所），**自动化测试一律用临时端口**，不要占用它们。

## 2. 停止

```
deploy/dev_stop.sh
```

按 控制台 → 内核 → 替身 的顺序停。内核先写停用标记 `var/run/kernel.nosupervise`（守护看到它就不再拉起），再发 SIGTERM，最多等 30 秒，
超时 SIGKILL；全部停掉后删除该标记（谁写谁删）。退出码 0 全部停掉；1 有进程无法终止。

只想让内核停止开仓、不关进程：在控制台点「停止」，或 `python -m dmr_kernel.cli stop`。停止只关开仓闸并撤未成交的开仓单；
已有仓的止损更新、信号平仓照常进行。

## 3. 状态

- `deploy/dev_status.sh`：每个进程的进程号、是否存活、健康检查；全部健康退出 0，否则 1。
- `python -m dmr_kernel.cli status`：用中文打印内核状态要点（环境、生效模型、闸位、抑制原因、权益、持仓计数、数据流与对账、席位、当前身份）。
  需要本机令牌 `var/kernel/local.token`（内核每次启动重写，权限 0600，只有同一系统用户读得到）；令牌不会被打印。
- 日志：`var/log/kernel.log`、`standin.log`、`console.log`（各 10MB×5 轮转，时间一律 UTC）、`supervise.log`；`*.out` 是原始标准输出，启动失败先看它。
- 应急入口的日志：`var/log/emergency.log`（追加写，每行带 UTC 时间）。

## 4. 首个操作员、登录与端口转发

### 4.1 创建首个操作员

操作员只能由命令行在内核主机上创建（控制台不提供注册入口）：

```
.venv-kernel/bin/python -m dmr_kernel.cli create-operator --username alice
```

口令由命令行随机生成（43 个字符），先以 0600 独占创建口令文件 `var/operators/alice.password`，再请内核创建账号；终端上**只打印口令文件的路径，
不打印口令**，也不能经环境变量或命令行参数指定口令。操作者从口令文件取出口令，**妥善保管后删除该文件**：内核只保存口令的哈希，丢了无法找回
（再创建同名用户会被拒绝，需要另用一个用户名）。

- 创建失败（内核拒绝、连不上）会自动删掉口令文件；结果不确定（请求发出后没拿到答复）时**保留**口令文件，先用其中的口令登录试一试，能登录就不用再做什么。
- 用户名只能是 1–32 位字母、数字、下划线、点或连字符。

### 4.2 登录与端口转发

控制台只绑 `127.0.0.1:18210`，内核只绑 `127.0.0.1:18200`，**两者都不对外开放**。从自己的电脑访问时用 SSH 端口转发：

```
ssh -L 18210:127.0.0.1:18210 <用户>@<服务器>
```

保持这个 SSH 连接，在本机浏览器打开 `http://127.0.0.1:18210`，用上面创建的用户名和口令登录。**不要**转发 18200（内核控制接口给命令行和控制台用）
或 18220（替身交易所）。不要把控制台改绑 `0.0.0.0` 或放到反向代理后面（脚本也会拒绝非回环地址）。

登录后同一时刻只有一个会话持有操作席位，其余只读；闲置超过设定时间（`session_idle_min`）会话过期。一键全平、切换、实盘启动要求最近
`reauth_window_s` 秒内重新输入口令。控制台与内核失联时，所有按钮禁用，并提示改用命令行应急入口或直接在 Binance 处置。

## 5. 恢复中的处理（`/ops/recover`）

内核启动后的「重启恢复」会逐项核对：交易所持仓与账本、在途订单、保护单、停机期间的成交（F9）。状态条显示「恢复中」表示还没完成。

1. **先等**：正常情况下几十秒内完成，状态条自动变成「已停止」。期间只能停止、平掉此仓、一键全平。
2. **一直是恢复中**：看 `var/log/kernel.log` 里 `recovery_*` 开头的告警（见第 9 节），以及 `python -m dmr_kernel.cli status` 里的抑制原因。
   常见原因：交易所读不到（替身没起来、限频）、有账本里没有的持仓需要人工归类、停机期间的成交补记失败。
3. **原因已排除后重新恢复**：`POST /api/v1/ops/recover`（请求体 `{"op_id": "<自拟的操作号>"}`；控制台总览页有对应按钮）。只在「恢复中」且上次恢复报了问题时可用，
   需要操作席位或本机令牌；结果 `{"tradable","problems","duration_ms"}` 写进操作记录：问题全部解决为成功，仍有问题为部分成功，`problems` 逐条列出剩下的。
4. 仍然不行、又需要立刻处置持仓：用 `python -m dmr_kernel.cli close-all`（内核存活）或第 6.2 节的应急路径。**不要**为了让恢复过去而删除账本或手工改库。

## 6. 应急：两条路径

先判断内核还活不活：`python -m dmr_kernel.cli status` 能出结果、控制台没有「与内核失联」提示 → 内核存活，走 6.1；连不上、卡死、没有答复 → 走 6.2。

### 6.1 内核存活：经控制接口

凭本机令牌（主体 `cli`）调用控制接口，不需要操作席位和口令；每次调用在内核里写操作日志。

```
python -m dmr_kernel.cli stop         # 关上开仓闸，撤未成交的开仓单
python -m dmr_kernel.cli close-all    # 全部托管持仓市价平仓
```

`close-all` 的范围固定为**全部托管持仓**（不含待确认与外部的仓；那些用 `inventory` 看，用控制台或第 7 节处理）。它先打印预览（会平哪些、不平哪些及原因），
等你输入 `y` 确认（`--yes` 跳过确认，只给脚本用），再提交并每秒轮询操作结果，逐仓打印：已平、已被外部平掉、失败、结果未知、有残余。
最多等 180 秒；超时只是不再等，内核里的操作继续，用 `status` 查看进展，**不会重发**。请求发出后没拿到完整答复时同样不重发，先核对再决定。
退出码 0 表示全部成功；部分成功、失败、已中止、结果未知都是 1。

### 6.2 内核不可用：`emergency close`

```
python -m dmr_kernel.cli emergency close
```

这是唯一绕过内核直接写交易所的路径，**只在内核失联、卡死或崩溃循环、而持仓必须处理时使用**。它按顺序做：

1. 写停用标记 `var/run/kernel.nosupervise`，守护看到它就不再拉起内核。
2. 按 `var/run/kernel.pid` 给内核发 SIGTERM，等最多 30 秒；不退出就 SIGKILL，并确认进程已不存在（仍存在则停下，不继续）。
   发信号前先核对该进程的命令行确实是内核；对不上就拒绝，什么信号也不发（进程号可能已被别的进程复用）。
3. 取 `var/kernel.lock`。取不到就拒绝执行（说明内核或另一个应急入口还在）；运行期间一直持有，结束才释放。
4. 用应急专用写权限和替身的 kernel 令牌（`var/standin/kernel.token`）连交易所，读**全账户持仓**，逐仓列出（它没有账本，分不清托管仓、外部仓、待确认仓，所以必须逐个确认），
   你对每一仓回答：`y` 平掉、`n` 跳过、`q` 退出（后面的都不处理）。确认后发市价平仓单，编号带应急前缀 `DKE-`。
5. 某仓**确认归零后**才撤该合约该方向上带系统前缀的条件单（止损等），避免它们作用到之后的新仓；没归零就不撤，保护留在交易所。
   用户自己的条件单（没有系统前缀）原样保留。
6. 结果打印并追加写 `var/log/emergency.log`。**不打开数据库。**

`--yes` 跳过逐个确认，**只给测试使用**；真实处置请逐个确认。退出码：0 全部处理完；1 有仓被跳过、未归零或被拒，或前置步骤失败；3 读不到交易所的持仓（没有下任何单）。

结束时命令会提示：「停用标记仍在，确认后删除 var/run/kernel.nosupervise 再启动内核」。**它不会自动删除标记**：

1. 到交易所（或 `inventory`、控制台）核对持仓与条件单，确认处置结果；
2. 查清内核当初为什么不可用（`var/log/kernel.log`、`var/log/kernel.out`），先修好；
3. `rm var/run/kernel.nosupervise`，再 `deploy/dev_start.sh`（标记还在时脚本退出码 3，拒绝启动）。

内核启动后的恢复会按交易所的成交记录补记这些平仓，成交来源记为「应急入口」；恢复完成前状态条显示「恢复中」（见第 5 节）。

## 7. 上线清点（`inventory`）

首次启动内核、或任何怀疑账户上有「不是系统开的」仓位和挂单时，先清点：

```
python -m dmr_kernel.cli inventory
```

只读，经控制接口列出：全部持仓（托管中、接管中、平仓中、待确认、外部/已忽略）和全部挂单（账本里的系统订单、交易所普通挂单、条件单；没有系统编号的标「外部」），
并给每一项可选的动作提示：**平掉**（控制台「平掉此仓」，或 `close-all` 平掉全部托管仓）、**接管**、**忽略**（后两项 M3 起可用）。
**本命令只列出与提示，不会自动执行任何动作。** 若提示「内核还没有取到交易所的挂单快照」，说明对账还没跑过，稍等再清点。

上线前核对：没有无保护的仓；没有来源不明的待确认仓（或已逐个决定平掉/接管/忽略）；交易所上没有旧程序遗留的条件单。
若将来在这台机器上启用 tmux 自动恢复，核对恢复名单里没有 python。

## 8. 回滚

### 8.1 回滚到旧系统（M7 起；替身阶段不适用）

1. `python -m dmr_kernel.cli stop`，需要时 `close-all`；确认无未处理的仓后 `deploy/dev_stop.sh`（内核退出时释放它持有的 7 把旧入口锁）。
2. 人工删除 `DMR_WebUI/data/runtime_state/LEGACY_DISABLED`（停用标记：上线时由操作者创建，内核既不创建也不删除）。
3. 作废新内核的交易密钥，恢复旧密钥。
4. 先用 `inventory` 或 Binance 核对仓位和条件单，再启动旧入口。

### 8.2 回滚新版本（代码）

`webui/` 是独立的 git 仓库（没有远程）。升级前先跑一次 `deploy/backup_drill.sh` 并记下当前提交；回滚时 `deploy/dev_stop.sh`，
签出升级前的提交，再 `deploy/dev_start.sh`。账本由迁移向前升级、不支持降级：升级前的在线备份（迁移前自动做）就是回滚点，见第 8.3 节。

### 8.3 回滚账本（用备份）

仅在账本损坏或迁移出错时做，**先停内核**：

1. `deploy/dev_stop.sh`。
2. 先演练：`deploy/backup_drill.sh --file backup/ledger-<时间戳>.sqlite`，通过（退出码 0）才继续。
3. 把坏的库连同 `-wal`、`-shm` 一起**挪到别处**（不要删）：`mv var/kernel/ledger.sqlite* /somewhere/safe/`。
4. 用 `restore_backup` 把备份恢复到原位置（它拒绝覆盖已有的库，所以第 3 步必须做）：
   `.venv-kernel/bin/python -c "from pathlib import Path; from dmr_kernel.ledger.backup import restore_backup; restore_backup(Path('backup/ledger-<时间戳>.sqlite'), Path('var/kernel/ledger.sqlite'))"`
5. `deploy/dev_start.sh`，等恢复完成后 `inventory` 核对：备份之后发生的成交会在恢复里按交易所记录补记，但**备份之后的操作日志和人工确认会丢**，需人工重做。

## 9. 备份恢复演练

内核每小时在线备份账本到 `backup/`（在 `var/` 之外，文件名 `ledger-<UTC 时间戳>[-标签].sqlite`），迁移前也自动备份一次。**每次升级前、以及每周**演练一次：

```
deploy/backup_drill.sh                      # 最新的备份
deploy/backup_drill.sh --file backup/ledger-20251009T085320.000Z.sqlite
deploy/backup_drill.sh --keep               # 保留恢复出来的库，排查用
```

它把备份恢复到临时目录并检查 `integrity_check`、`foreign_key_check`、每张表的行数、与备份文件逐字节比对，打印结果后删除临时目录；
**不碰正在使用的账本**。退出码 0 通过；1 恢复或检查失败；2 用法错误或没有备份。备份目录之外还要每日打包到 DMR_WebUI 目录之外（另行安排）。
演练失败时不要升级，先查 `ledger_backup_failed` 告警（见下节）。

## 10. 常见告警

告警在控制台状态条和「告警」列表里显示，也可经 `GET /api/v1/alerts` 查看；配置了 Apprise 地址（`DMR_ALERT_URLS`）才会推送。
级别：info 信息、warning 警告、critical 严重。下表按类型列出现象与处理，**严重级别一律先看日志再动手，不要反复点重试**。

| 类型（kind） | 含义 | 处理 |
|---|---|---|
| `protect_unprotected`、`protect_failed_closing`、`protective_close_failed` | 有仓没有止损，或补保护失败后已尝试平仓/平仓也失败 | 立即 `inventory` 看该仓；确认交易所上有没有条件单；处理不了就 `close-all` 或 6.2 |
| `stop_missing_rebuilt`、`protect_restored` | 止损被撤后已自动重建 / 保护已恢复 | 信息；留意是谁撤的（外部操作） |
| `external_protection_lost`、`orphan_stop_kept` | 外部仓的止损丢失 / 留下了孤儿止损 | 在 `inventory` 里决定平掉、接管或忽略 |
| `reconcile_mismatch`、`reconcile_mismatch_stop` | 对账发现账本与交易所持仓不一致（严重时已停止开仓） | 查清原因后在控制台人工确认解除（`reconcile_mismatch_confirmed`）；不确定就先停止、`inventory` 核对 |
| `reconcile_unknown`、`reconcile_orders_unknown` | 持仓/挂单读不到，对账状态未知 | 通常是交易所不可达或限频；恢复后会自动出 `*_cleared` / `*_recovered` |
| `position_closed_by_reconcile` | 对账发现某仓已在交易所被平掉 | 核对是否人为平仓 |
| `liquidation_before_stop` | 强平发生在止损之前 | 严重：复盘止损距离与杠杆，暂停开仓 |
| `exchange_auth_failed` | 交易所拒绝了令牌/密钥 | 检查替身令牌文件 `var/standin/kernel.token`（实盘为密钥，M7 起）；不要在日志里找密钥 |
| `exchange_restricted`、`exchange_restriction_lifted` | 交易所限制了交易 / 限制解除 | 限制期间不开仓；解除后确认再启动 |
| `position_mode_not_hedge` | 账户不是对冲持仓模式 | 在交易所改回对冲模式；改好前不能启动 |
| `stream_interrupted`、`stream_recovered` | 账户数据流中断 / 恢复 | 中断期间降级为轮询；长时间不恢复检查网络与替身 |
| `clock_skew`、`clock_skew_cleared` | 本机时间与交易所偏差过大 / 恢复 | 校准系统时间（NTP） |
| `recovery_done` | 重启恢复完成 | 信息 |
| `recovery_blocked`、`recovery_incomplete`、`recovery_step_failed`、`recovery_snapshot_unknown`、`recovery_backfill_failed` | 恢复没能完成某一步，内核留在「恢复中」 | 见第 5 节：先排除原因，再 `/ops/recover` |
| `recovery_unregistered_position` | 恢复时发现账本里没有的持仓 | 用 `inventory` 逐个决定平掉、接管或忽略 |
| `recovery_closing_resumed`、`recovery_closing_resume_failed`、`recovery_closing_unresolved` | 崩溃前正在平的仓：已续平 / 续平失败 / 未决 | 失败或未决的用 `inventory` 核对后手工平掉 |
| `operation_interrupted` | 批量操作被中断（例如内核重启） | 用 `inventory` 核对，必要时重新 `close-all` |
| `risk_daily_loss_tripped`、`risk_drawdown_tripped`、`risk_model_tripped`（及 `*_reset`） | 风控限额触发（已停止开仓）/ 已重置 | 触发后不要急着重置；复盘后再决定 |
| `legacy_fill_detected` | 发现旧程序格式编号的新成交（有漏网的旧进程） | 严重：已关上开仓闸；找到并停掉旧进程，再启动 |
| `legacy_mutex_anomaly`、`legacy_mutex_restored` | 旧入口互斥（7 把锁/停用标记）异常 / 恢复（实盘） | 检查 `DMR_WebUI/data/runtime_state/` 下的锁与 `LEGACY_DISABLED` 是否被清理 |
| `ledger_backup_failed`、`ledger_wal_large` | 账本备份失败 / WAL 文件过大 | 查磁盘空间与 `backup/` 权限；备份恢复演练失败前不要升级 |
| `heartbeat_write_failed` | 内核写不了心跳文件 | 查 `var/kernel/` 权限与磁盘；心跳停止超过 60 秒，外部看护（`heartbeat_watch.py`）会推送告警 |
| `intent_late_fill` | 一笔已判定失败的意图后来成交了 | 严重：`inventory` 核对该仓是否有保护 |
| `cancel_attempts_exhausted` | 撤单多次失败 | 到交易所手工撤，并核对仓位 |
| `stop_crossed_closing`、`stop_gap_exceeded` | 价格已穿过止损 / 跳空超过阈值，正在平仓 | 核对平仓结果 |

## 11. 禁止事项

- 不要读取、打印或提交 `.env`、交易所密钥、`var/**/*.token`、`var/operators/*.password`（命令行也不会把它们打印出来）。
- 不要运行旧入口与旧脚本（`DMR_WebUI` 根目录下的 `main.py`、`*_main.py`、`start_trading.sh` 等）；不要在 `DMR_WebUI` 根目录跑 pytest。
- 不要手工改账本（`var/kernel/ledger.sqlite`）；要读它请先停内核或用备份副本。
- 不要在内核运行时运行 `emergency close`：它会先停掉内核。内核存活就用 `stop` / `close-all`。
- 不要自动或脚本化地删除停用标记 `var/run/kernel.nosupervise`；谁写谁删，应急入口写的由操作者确认后手工删。
