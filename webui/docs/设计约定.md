# DMR WebUI 设计约定（本轮：替身环境可验收版本）

本文是实施时各模块之间的**约定**，写给接手实现的人或 AI。设计基线是计划报告
`DMR_WebUI/A_MD/Claude_Opus5.5_DMR量化策略程序源代码增加WebUI功能的落地执行计划分析.md`（下称「报告」）；
本文把报告落到本轮的具体接口、表结构和协议上。与报告不一致的地方都记在 `docs/实施记录.md`。

代码里已经落地、以代码为准的部分：
- 共享类型与枚举：`dmr_kernel/core/types.py`
- 事件总线与事件类型：`dmr_kernel/core/events.py`
- 配置项定义：`dmr_kernel/core/configdefs.py`
- 适配层接口与写方法出口校验：`dmr_kernel/exchange/adapter.py`
- 订单编号：`dmr_kernel/exchange/ids.py`
- 结构规则检查：`tests/unit/test_structure_rules.py`（第 5 节的分层表与它一致）

## 1. 硬性规则（每个实施者都必须遵守，违反任何一条都要先停下来报告）

1. **不碰密钥和私有接口**。不读取、不打印、不复制 `DMR_WebUI/.env` 或任何密钥。不调用 Binance 的任何私有接口
   （下单、撤单、账户、持仓、listenKey、账户数据流）。对 Binance 只允许公共行情和合约规则的 GET 请求，经 ccxt 4.5.78
   的公共方法，ccxt 实例上不配置任何 apiKey/secret。
2. **不运行任何旧入口或旧脚本**：任何 `*_main.py`、`main.py`；`start_trading.sh` 的任何子命令、`bit/start_*.sh`、
   `bit/config/switch_model.py`；`deploy_and_run.sh`、`cleanup_deployment_files.sh`；`tests/test_security_fixes.py`、
   `tests/test_config_sync.py`。不在 `DMR_WebUI/` 根目录跑 pytest；只用 `webui/run_tests.sh`。不运行 `python -m compileall`。
3. **只改 `DMR_WebUI/webui/` 里的文件**。`DMR_WebUI/` 的其它文件一律不改（`.gitignore` 与清理脚本的两处改动已在 M0 完成）。
   `A_MD/`、`bit/B_MD/`、`bit/data/config/model_state.json` 不动。**替身环境下不打开 `DMR_WebUI/data/runtime_state/` 里的任何文件**；
   旧入口互斥的测试一律用临时目录。
4. **不导入 DMR 模块**。内核、控制台、替身交易所运行时都不导入 DMR 的任何模块（`common`、`config`、`bit`、`strategy` 等）。
   对拍测试只以**只读方式**引用 DMR 的源码文本和 CSV：用 `ast` 按名字或行段取出源码，在隔离的命名空间里编译执行；
   不经 import 系统导入 DMR 模块，不写字节码，不在 DMR 目录里产生任何文件。
5. **git 只在 `webui/` 自己的仓库里写**，不配置任何远程。`DMR_WebUI` 自己的仓库一律不做 git 写操作（add、commit、push、
   reset、clean、stash、worktree 都不行）。并行实施时实施者**不提交**，由编排者按任务提交。
6. **解释器只用显式路径**：`webui/.venv-kernel/bin/python`、`webui/.venv-console/bin/python`。shell 的 PATH 上激活的是
   `DMR_WebUI/venv`，不要用裸的 `python`、`pip`、`pytest`。**不安装任何包**；需要新依赖时停下来报告。不用 aiosqlite。
   只用 GitHub 不低于 3000 星、非 GPL/AGPL 的组件。
7. **选币名单只读**：只允许 `GET http://127.0.0.1:18080/api/v1/onlycoin/live`（不带任何查询参数）。不得调用
   `/api/v1/onlycoin/sources/screener-y/status`（它的 GET 也会写数据），不得调用任何 PUT。测试一律用本地假名单或录制样例，
   不连真实接口。
8. **监听只绑回环**：内核 `127.0.0.1:18200`，控制台 `127.0.0.1:18210`，替身交易所 `127.0.0.1:18220`。
   测试里需要起服务的一律用临时端口（端口 0），不占用上面三个正式端口（验收演示期间它们一直在运行）。
9. **禁网测试**：除 `tests/e2e_local/` 外，所有测试都在 `tests/guard/no_network_ip.py` 包装下运行（`./run_tests.sh kernel|console`），
   进程里连回环都连不上。需要真实进程和回环的放 `tests/e2e_local/`，只用回放行情和假名单（`./run_tests.sh e2e`）。
10. **遇到下面的情况先停下来报告，不要绕过**：需要改 `webui/` 以外的文件；需要 PyPI、Binance 公共接口、本机名单接口以外的网络；
    需要任何密钥；某条规则与报告无法同时满足。

## 5. 分层（与 `tests/unit/test_structure_rules.py` 一致，改这里就要同时改那里）

一个模块只能导入比自己低的层；同层不同组之间不直接导入，靠 `core.events` 通知。分组：`core.*` 与 `models.*` 每个模块各成一组，
其余按包成组（例如 `exchange.*` 是一组，组内可以互相导入）。

| 层 | 模块 |
|---|---|
| 0a | `core.types`、`core.clock`、`core.crashpoints`、`core.configdefs`、`core.lifecycle`、`settings`（纯定义与标准库工具；0a 之间只允许导入 `core.types`） |
| 0b | `algo`、`core.events` |
| 1 | `exchange`、`ledger` |
| 2 | `marketdata`、`listsync`、`alerts`、`core.config` |
| 3 | `core.modelstate`、`core.registry`、`core.intents`、`core.orders`、`core.ingest`、`core.riskgate`、`core.limits` |
| 4 | `core.coordinator` |
| 4.5 | `models.base`（只给 `models.*` 用） |
| 5 | `core.protection`、`core.reconcile`、`core.guard`、`models.m1_strategy`、`models.m2_takeover`、`models.m3_reserved` |
| 6 | `core.recovery`、`ops` |
| 7 | `api`、`cli`、`core.scheduler` |
| 8 | `__main__` |

库的使用范围：`sqlalchemy`/`alembic`/`sqlite3` 只在 `ledger`；`ccxt` 只在 `exchange`；`apprise` 只在 `alerts`；
`apscheduler` 只在 `core.scheduler`；`fastapi`/`starlette` 只在 `api`；`uvicorn` 只在 `api`、`core.scheduler`、`__main__`。
内核、控制台、替身交易所三个包互不导入（控制台只经 HTTP/WebSocket 调内核；替身交易所是独立的「外部系统」）。

四条结构规则（报告 4.1）的落点：
1. **只有协调者能调用适配层的写方法**：写方法必须出示 `WriteCapability`；令牌由 `core.scheduler` 创建一次并只交给
   `Coordinator`；应急入口自建 `owner="emergency"` 的令牌。静态检查保证写方法只在 `core.coordinator`、`cli.emergency` 被调用。
   协调者自己的公开方法不要用 `cancel_order` 这类与适配层写方法同名的名字。
2. **只有内核进程能打开数据库，库里只有账本模块写**：SQL 与 ORM 代码只在 `ledger/`；上层调用 `ledger` 里的仓储函数，
   经单写线程执行（第 8 节）。控制台、命令行、备份都经内核完成。
3. **算法包没有任何 I/O**：静态检查禁止导入 os/time/datetime/logging 等，禁止 open/print，禁止读时钟。
4. **下层不导入上层**：见上表。

## 6. 通用约定

- **时间**：一律 UTC 毫秒（int，字段名 `*_ms`）。数据库存整数毫秒。只有界面层换成本地时间显示（本机 +07）。
  需要「现在」的地方注入 `core.clock.Clock`，测试用 `ManualClock`。
- **数值**：价格、数量、金额一律 `Decimal`；数据库里存成文本（`ledger` 提供 `DecimalText` 类型）；JSON 里一律是字符串。
  只有交给 pandas 的 K 线字段是 float；算法算出的价格在边界处转 `Decimal(str(x))` 并按价格步长取整。
- **合约**：一律用交易所原始代码（`BTCUSDT`、中文合约名照原样）；ccxt 的统一写法只在 `exchange.binance*` 里出现。
- **方向**：持仓方向 `LONG`/`SHORT`，买卖方向 `BUY`/`SELL`（`core.types`）。对冲模式下下单直接带持仓方向，不传只减仓标记。
- **订单编号**：见 `exchange/ids.py`。系统编号 `DK<实例>-<模型>-<意图号36进制>-<分腿>`；实例 = 设置里的实例号 + 账本建库时生成的
  2 位随机串（存在账本 `meta` 表的 `ledger_nonce`）。模型代码 1/2/3 是三个模型，0 是操作员与系统动作。分腿：`o` 开仓、
  `c` 平仓、`p` 部分平仓、`s` 止损、`d` 碎仓条件单；重发用 `ids.resend_leg`（`c1`、`c2`…，一律换新编号，实测第 13 项）。
- **语言**：标识符英文；面向用户的原因、告警、界面文字用中文；注释简短。
- **日志**：标准库 logging，每模块 `logging.getLogger(__name__)`；只在 `__main__` 配置处理器（按大小轮转，`var/log/`）。
  永远不记令牌、口令、密钥。
- **错误**：程序错误（违反约定）抛异常；交易所的拒绝与未知走 `WriteRejected`/`WriteUnknown`/`Unknown` 等结果类型。
  「未知」绝不能当成「空」或「不存在」。

## 7. 替身交易所（dmr_standin）

定位：只用于开发和验收，不是产品功能（报告 1.4 把本地模拟撮合列为不做）。必须是**独立进程**：「进程被杀后重启」
「停机期间止损触发」两种故障注入要求交易所在内核停机时继续运行。

### 7.1 结构

- `engine.py`：账户、合约规则、持仓（对冲两侧）、订单、条件单、成交、收益流水、撮合与触发、资金费、权重计数。纯内存、
  可注入时钟与行情源；提供 `check_triggers()` 供测试直接驱动。
- `feed.py`：行情源。`BinancePublicFeed`（ccxt 4.5.78 公共方法，无密钥，单实例长连接，每个请求设超时）、
  `ReplayFeed`（回放 `DMR_WebUI/bit/data/` 下的 CSV + 内置合约规则样例 `data/instruments_sample.json`）、
  `StaticFeed`（测试用，价格与 K 线由测试设定）。`auto` 模式启动时先试 Binance（合约清单 + 一次 K 线，20 秒内），
  失败就整次运行用回放，并在 `feed_status` 里标明来源。
- `faults.py`：故障开关与行为开关（7.5）。
- `dispatcher.py`：**与传输无关**的请求分发：`handle(method, path, params, body, headers) -> (status, body, headers)`，
  以及账户数据流的订阅中心。FastAPI 应用（`server.py`）只是它的 HTTP/WebSocket 外壳。
  内核的集成测试在禁网包装下用进程内传输直接调用分发器（`tests/support/`），走的是同一套请求解析与撮合代码。
- `persistence.py`：状态快照 `var/standin/state.json`（原子写，变化后 1 秒内落盘）与操作留痕 `var/standin/ops.log`。
- `__main__.py`：`python -m dmr_standin [--host 127.0.0.1] [--port 18220] [--state-dir var/standin] [--feed auto|binance|replay]
  [--equity 1000] [--no-persist] [--replay-dir <DMR_WebUI>/bit/data]`；只允许回环地址；首次启动生成两把令牌（0600）。

### 7.2 HTTP 协议

基址 `http://127.0.0.1:18220`。成功返回 200 与 JSON；失败返回 Binance 风格的 `{"code": int, "msg": str}`：业务拒绝 400，
限频 429（或 418）带 `Retry-After`，执行状态未知 503（`{"code": -1007, "msg": "Timeout waiting for response from backend
server. Send status unknown; execution status unknown."}`）。每个响应带 `X-MBX-USED-WEIGHT-1M`（滚动 1 分钟的已用权重）。
所有数值字段是字符串，时间是毫秒整数。

**公共**（无需令牌）：

| 方法 | 路径 | 返回 |
|---|---|---|
| GET | `/api/public/time` | `{"server_time_ms"}` |
| GET | `/api/public/instruments` | `[instrument]`，字段同 `core.types.Instrument`：`symbol base quote contract_type status tick_size step_size min_qty min_notional market_step_size market_max_qty onboard_ms` |
| GET | `/api/public/klines?symbol=&interval=15m&limit=99` | `[[open_time_ms, "o", "h", "l", "c", "v", close_time_ms], ...]` 升序；最后一根可能未收盘；limit ≤ 99 |
| GET | `/api/public/tickers[?symbols=A,B]` | `{"BTCUSDT": {"symbol","last","mark","time_ms"}}` |
| GET | `/api/public/feed_status` | `{"source": "binance"|"replay"|"static", "healthy", "last_ok_ms", "errors"}` |

**私有**（请求头 `X-Standin-Key: <kernel.token>`）：

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/private/account` | `{"equity","wallet_balance","available_balance","unrealized_pnl","update_time_ms"}` |
| GET | `/api/private/position_mode` | `{"dual_side": true}` |
| GET | `/api/private/positions` | 只含数量非零：`[{"symbol","position_side","qty","entry_price","mark_price","liquidation_price","unrealized_pnl","leverage","margin_mode","update_time_ms"}]` |
| GET | `/api/private/open_orders[?symbol=]` | `[order]` |
| GET | `/api/private/open_algo_orders[?symbol=]` | `[algo]` |
| GET | `/api/private/order?symbol=&client_order_id=` 或 `&order_id=` | `order`；不存在 400 `{"code": -2013}` |
| GET | `/api/private/algo_order?symbol=&client_algo_id=` 或 `&algo_id=` | `algo`；不存在 400 `-2013`（条件单编号只在未结条件单内唯一：已结束的按 algo_id 查） |
| POST | `/api/private/order` | 体 `{"symbol","side","position_side","type":"MARKET","qty","client_order_id"}` → `order` |
| POST | `/api/private/algo_order` | 体 `{"symbol","side","position_side","type":"STOP_MARKET"|"TAKE_PROFIT_MARKET","trigger_price","working_type","close_position",`"qty"`(全平型为 null),"client_algo_id"}` → `algo` |
| DELETE | `/api/private/order?symbol=&client_order_id=`（或 `order_id`） | `order`（CANCELED）；不存在 400 `-2011` |
| DELETE | `/api/private/algo_order?symbol=&client_algo_id=`（或 `algo_id`） | `algo`（CANCELED）；不存在 400 `-2011` |
| GET | `/api/private/trades?symbol=&start_ms=&end_ms=&limit=` | `[trade]`，**不带自定义编号**（与 Binance REST 一致，用 `order_id` 关联） |
| GET | `/api/private/income?start_ms=&end_ms=&type=&limit=` | `[{"tran_id","type","symbol","amount","asset","time_ms","info"}]`（FUNDING_FEE、REALIZED_PNL、COMMISSION） |
| GET/POST | `/api/private/leverage` | GET `?symbol=` → `{"symbol","leverage","margin_mode"}`；POST `{"symbol","leverage"}` |
| POST | `/api/private/margin_mode` | `{"symbol","margin_mode"}`；该合约有仓 400 `-4048`，有挂单 400 `-4047` |
| GET | `/api/private/trading_status` | `{"restricted": bool, "detail": {...}}` |
| POST / PUT | `/api/private/listen_key` | POST → `{"listen_key","expires_ms"}`；PUT `{"listen_key"}` 续期 → `{"expires_ms"}`；60 分钟不续期即失效 |

`order` = `{"symbol","client_order_id","order_id","side","position_side","type","qty","filled_qty","avg_price","status","raw_status","close_position","reduce_only","update_time_ms"}`；
`algo` = `{"symbol","client_algo_id","algo_id","side","position_side","type","trigger_price","working_type","close_position","qty","status","actual_order_id","create_time_ms","update_time_ms"}`（`status` 是交易所原始状态：NEW、TRIGGERING、TRIGGERED、FINISHED、CANCELED、EXPIRED、REJECTED）；
`trade` = `{"trade_id","order_id","symbol","side","position_side","qty","price","commission","commission_asset","realized_pnl","time_ms","maker"}`。

错误码（适配层据此归类成 `core.types.RejectKind`）：−2021 会立即触发；−4130 同向已有全平型止盈止损；−2022 无仓可平或超出持仓；
−4164 名义金额不足；−2019 保证金不足；−4116 编号重复；−2011/−2013 订单不存在；−4045 条件单数量到上限；−1003 限频；
−4047/−4048 有挂单或持仓时不能改保证金模式；−1102/−1111/−4015 参数错误；HTTP 503/−1007/−1001 执行状态未知。

### 7.3 账户数据流

`GET /ws/stream?listen_key=...`（WebSocket，文本 JSON）：

- `{"type":"order_update","event_time_ms","execution":"NEW|TRADE|CANCELED|EXPIRED|REJECTED","order":{order},"fill":{trade}|null}`（带自定义编号）
- `{"type":"algo_update","event_time_ms","algo":{algo}}`（只在行为开关 `push_algo_events` 打开时推送，实测第 11 项）
- `{"type":"account_update","event_time_ms","reason":"ORDER|FUNDING_FEE|...","positions":[position...],"balances":[{"asset","wallet_balance"}]}`
- `{"type":"listen_key_expired","event_time_ms"}`
- `{"type":"heartbeat","server_time_ms"}`：每 10 秒一帧。内核判活看「任何帧」，不看业务事件。

内核侧的数据流（`exchange.stream.StandinAccountStream`）没有内部定时器：续期、静默判活、listenKey 过期判活、退避重连、稳定窗口都在
`AccountStream.check_liveness()` 里按注入的时钟评估，调度器至少每 5 秒调用一次；`listen_key_expired` 帧例外，读循环里立即重建。

### 7.6 撮合规则

- 市价单按当前最新价成交；手续费按名义金额的 0.05%（USDT）；默认杠杆 20、全仓（与 Binance 新合约默认一致），可被内核修改。
- 对冲两侧独立：`BUY LONG` 开/加多，`SELL LONG` 减多，`SELL SHORT` 开/加空，`BUY SHORT` 减空。减仓超量按 `close_qty_exceeds`；
  该侧无仓时 −2022。开仓单低于最小名义金额 −4164；平仓单是否豁免按 `close_min_notional_exempt`。开仓保证金不足 −2019。
- 持仓均价按加权平均；减仓时实现盈亏 = (出场价 − 均价) × 数量（空仓反号），计入钱包余额；权益 = 钱包余额 + 浮动盈亏。
- 强平价按简化公式估算：多 `均价 × (1 − 1/杠杆 + 0.5%)`，空 `均价 × (1 + 1/杠杆 − 0.5%)`；只用于展示和「强平价比止损价更近」的告警，替身不执行强平。
- 条件单：止损多仓（SELL）在价 ≤ 触发价时触发，空仓（BUY）在价 ≥ 触发价时触发；止盈相反。触发价类型 `CONTRACT_PRICE` 看最新价，
  `MARK_PRICE` 看标记价。建单时已被越过按 `stop_crossed_on_create`。同向第二张全平型止损按 `dual_close_position_stop`。
  条件单数量上限按 `conditional_limit`（−4045）。触发后生成市价单：全平型平掉该侧全部持仓，数量型按数量（持仓变小后按
  `qty_stop_after_shrink`）；条件单状态变为 FINISHED（成交）或 EXPIRED（该侧已无仓）。仓位归零后全平型止损是否自动撤销按
  `close_position_stop_autocancel_on_flat`。
- 后台每秒检查一次触发；测试可直接调 `engine.check_triggers()`。
- 资金费：每天 00:00、08:00、16:00 UTC 对持仓结算（费率取 Binance 公共的资金费率；回放时取 0.01%），可用 `/dev/funding/settle` 立即结算。

## 8. 账本（SQLite，`ledger`）

访问方式（报告 4.5）：SQLAlchemy **同步**引擎加**单写线程**；连接参数 WAL、`synchronous=FULL`、`busy_timeout=5000`、
`foreign_keys=ON`；写事务 `BEGIN IMMEDIATE`；读用独立的只读连接在线程池里执行。迁移用 Alembic（SQLite 下用批量模式），
只在内核启动时、任何任务开始前执行，迁移前先做一次在线备份。

```python
ledger = Ledger.open(db_path, backup_dir=..., clock=...)   # 同步：建目录、备份、迁移、起写线程
await ledger.write(repo_fn, *args)   # 在写线程里开 BEGIN IMMEDIATE 事务执行 repo_fn(session, *args)，提交后返回
await ledger.read(repo_fn, *args)    # 在线程池里用只读会话执行
await ledger.backup(dest_dir)  await ledger.checkpoint()  await ledger.close()
ledger.nonce                          # 建库时生成的 2 位随机串（订单编号的实例部分）
```

`repo_fn` 是定义在 `ledger/repo_<领域>.py` 里的函数，签名 `fn(session, ...) -> 普通数据`（返回 `ledger/records.py` 里的
记录数据类或基本类型，**不返回 ORM 对象**）。上层模块不导入 sqlalchemy；某个上层模块需要新的读写，就在对应的
`ledger/repo_<领域>.py` 里加函数。「先落盘后下单」靠 `await ledger.write(...)` 返回才继续这一步保证。

## 9. 状态与规则

持仓登记簿的事件约定：新建发 `PositionRegistered`；其余变化发 `PositionChanged(cause, version)`（cause 取值：takeover、managed、
set_closing 调用方给的值、protection、stale_stops、handed_over、ignored、pending、fill、外部调整、qty_change）；归零只发 `PositionClosed`；
保护状态或止损价变化在 `PositionChanged` 之后再发 `ProtectionChanged`；`update_exchange_view` 不改版本、不发事件；一仓一主冲突抛 `KeyOccupied`，
版本过期抛 `StaleVersion`。已平的记录仍可改止损相关登记（归零后清理用）。

- 意图 10 态、订单 8 态、持仓 6 态、保护 4 态、出场规则集、模型状态四层（开仓闸、抑制原因、操作锁、运行方式）：见 `core.types` 与报告 4.6。
- **两种状态版本**：模型状态版本（全局；启动、停止、切换、一键全平校验）；持仓状态版本（每个持仓；部分平仓、平掉此仓、接管类操作校验）。
- **「状态与可执行操作」表（报告 4.6）由内核强制**：`core.modelstate.allowed_operations(state)` 返回每个操作是否可执行及原因；
  `ops` 每个入口先查它，界面置灰只是提示。模型 3 生效时启动一律拒绝。
- 「无保护持仓」「对账不一致」只针对登记仓（接管中、托管中、平仓中）；待确认仓和外部仓只在状态条上计数。名单无效不是抑制原因。

## 11. 控制台（NiceGUI）

只做三件事：登录、把内核状态画出来、把按钮变成对控制接口的调用。所有校验都在内核做。内核令牌只存在控制台服务端的内存里
（按浏览器会话），浏览器拿不到。内核失联时全部按钮禁用，并提示改用命令行应急入口或直接在 Binance 处置。
页面：登录、总览（四个统一操作 + 模型切换 + 按钮在当前模型下的含义）、持仓、名单、逐笔交易、统计、K 线、操作日志、设置
（含模型 3 配置页）、开发工具（只在替身环境：模拟手动下单、信号注入、故障开关、价格覆盖）。常驻状态条字段见报告 4.10。

## 12. 测试约定

- `./run_tests.sh kernel [路径]`：`tests/guard`、`unit`、`parity`、`standin`、`integration`、`faults`，内核环境 + 禁网包装。
- `./run_tests.sh console [路径]`：`tests/console`，控制台环境 + 禁网包装。
- `./run_tests.sh e2e [路径]`：`tests/e2e_local`，真实进程、回环、临时端口、回放行情、假名单，带 `@pytest.mark.e2e`。
- 协程测试直接写 `async def test_...`（`tests/conftest.py` 用 `asyncio.run` 执行），不用 pytest-asyncio。
- 测试先行：先写会失败的测试并确认它失败的原因是功能缺失，再写最小实现。每条规则有正反用例；4.7 的每个失败分支都有用例。
- `tests/support/`：进程内传输（直接调替身交易所的分发器）、`StaticFeed` 帮手、临时账本、内核装配帮手、假名单。
- 测试里不 sleep 等业务时间：用 `ManualClock` 推进，或调替身的 `check_triggers()`；需要真实等待的（超时）用很短的时限。

## 13. 中断点与故障注入

崩溃点名称见 `core/crashpoints.py`，对应报告 6.2 的 8 个中断点。进程内用 `CrashRegistry.arm` + `CrashSignal`
模拟被杀（丢弃整个内核实例、不走关停，再用同一账本与同一替身重新装配）；进程级用 `DMR_CRASHPOINT` + `os._exit(137)`。
九种故障的通过标准见报告 4.11，每种都在 `tests/faults/` 有用例，并进入每次都跑的测试集。
