# 交易意图约定

> 本约定由 `tests/unit/m5/test_m5_intent_convention.py` 固定：改字段、幂等键格式或状态机，要同时改这份文档和那个测试。
> 实现：`dmr_kernel/core/intents.py`（`IntentSpec`、状态机、幂等键）、`dmr_kernel/ledger/repo_intents.py`（intent 表）、`dmr_kernel/core/coordinator.py`（执行）。

## 1. 意图是什么

所有会改变交易所状态的动作（开仓、平仓、部分平仓、挂/改/撤止损、撤单、改杠杆与保证金模式）都先写成一条**交易意图**，落盘（intent 表）之后才由协调者执行。
意图只有一个出口：`Coordinator.submit(spec)`。没有落盘的意图不执行；同一个幂等键只会落一行、只会产生一笔订单。

## 2. IntentSpec 字段

| 字段 | 类型 | 必填 | 含义与取值 |
| --- | --- | --- | --- |
| `action` | `IntentAction` | 是 | `open`、`close`、`partial_close`、`stop_place`、`stop_replace`、`stop_cancel`、`order_cancel`、`set_leverage`、`set_margin_mode`。只有 `open` 新增风险，受开仓闸、抑制原因、风控闸约束。 |
| `model` | `str` | 是 | 发起方：`m1`（完全自动）、`m2`（接管）、`m3`（AI，预留）、`op`（操作员与命令行）。不能为空。 |
| `source` | `IntentSource` | 是 | 来源，见第 4 节。 |
| `symbol` | `str` | 是 | 合约，如 `BTCUSDT`。不能为空。 |
| `side` | `PositionSide` | 是 | 持仓方向 `LONG` 或 `SHORT`（对冲模式）。 |
| `idem_key` | `str` | 是 | 幂等键，格式见第 3 节。在 intent 表上唯一。不能为空。 |
| `qty` | `Decimal \| None` | 否 | 数量（基础币）；非负。平仓类用它表示部分平仓数量。 |
| `ratio` | `Decimal \| None` | 否 | 比例（如部分平仓 0.5）；非负。 |
| `params` | `Mapping[str, Any]` | 否 | 动作的附加参数（如 `trigger_price`、`notional`、名单快照号）。整体存 JSON。 |
| `reason` | `str` | 否 | 人能读懂的原因（入场原因等），会写进逐笔交易的入场原因。 |
| `ttl_s` | `int \| None` | 否 | 有效期（正整数秒）。过了有效期还没发出订单的意图置 `EXPIRED`，不会被执行；`None` 永不过期。 |
| `operator` | `str \| None` | 否 | 操作员名（操作类意图）。 |
| `op_id` | `str \| None` | 否 | 操作号（操作类意图，与 operation 表对应）。 |
| `position_id` | `int \| None` | 否 | 作用的持仓编号。 |
| `position_generation` | `int \| None` | 否 | 持仓代际（该「合约 + 方向」第几次从零开仓）。 |
| `parent_intent_id` | `int \| None` | 否 | 父意图（如反手的平仓步与开仓步）。 |
| `ai_eval_ref` | `str \| None` | 否 | **模型 3 接入位**：指向 AI 评估记录的引用（评估编号、模型版本、提示摘要的哈希等，由模型 3 自定）。内核只存不解释，原样写进 intent 表和影子留痕的审计记录；本期没有任何逻辑依赖它。 |

数值一律用 `Decimal`，接口出口转字符串；时间一律 UTC 毫秒整数。

## 3. 幂等键格式（一旦用过就不能改）

键存在 `intent.idem_key`。每一段里的 `%` 与 `:` 分别转义为 `%25` 与 `%3A`，保证拼出来的键不串味；方向取 `LONG`/`SHORT`。

| 用途 | 格式 | 样例 |
| --- | --- | --- |
| 开仓 | `open:<模型>:<合约>:<方向>:<信号 K 线开盘时间>`，反手的开仓步另加 `:rev<被平仓位代际>`，替身环境信号注入另加 `:inj<序号>` | `open:m1:BTCUSDT:LONG:1700000000000` |
| 反向信号平仓 | `sigclose:<合约>:<方向>:g<持仓代际>:<信号 K 线开盘时间>` | `sigclose:BTCUSDT:LONG:g4:99` |
| 操作员或命令行操作 | `op:<操作号>[:<合约>[:<方向>[:<分腿>]]]`（不给的部分留空位，尾部空位去掉） | `op:op-1:BTCUSDT:LONG:close` |
| 保护动作 | `protect:<持仓编号>:g<代际>:<用途>:<序号>` | `protect:7:g2:stop:1` |
| 影子记录（替身环境接口） | `shadow:<调用方给的引用>` | `shadow:shadow-1` |

同一个键再次提交：不写第二行，返回已有记录；还没发出订单的未到终态意图会（重新）派发，已经有订单的不会再发第二笔。

## 4. 来源 source

`signal`（模型 1 的自然信号）、`injected`（替身环境的信号注入）、`operator`（操作员）、`protection`（保护单管理）、`takeover`（接管）、
`reconcile`（对账修复）、`recovery`（重启恢复）、`test_entry`（非实盘测试造仓）、`cli`（命令行）、`shadow`（影子记录通道，模型 3 预留）、`system`（内部）。

## 5. 状态机（10 态）

`CREATED` → `VALIDATED` → `RESERVED`（占合约数名额）→ `DISPATCH_READY` → `ACTIVE` ⇄ `RECONCILING` → `COMPLETED`；
任何发出订单之前都可以到 `REJECTED`（放弃，带原因）、`EXPIRED`（过期）、`CANCELLED`（撤销）。
迁移表见 `core.intents.TRANSITIONS`；终态（`COMPLETED`、`REJECTED`、`EXPIRED`、`CANCELLED`）没有出口，唯一例外是系统订单的晚到成交把意图
重开为 `ACTIVE` 并告警。状态的检查与修改在账本的同一个写事务里完成。

## 6. 影子记录通道（模型 3 预留）

`source=shadow` 的意图在协调者的准入段**之前**被拦截：写一条 `shadow.intent` 审计，意图置 `REJECTED`，原因固定为「影子记录：只留痕不下单」。
不看开仓闸、名单、频率限制，不占合约数名额，**绝不产生订单**。任何动作（开仓、平仓……）一视同仁。
入口：`dmr_kernel.ops.shadow.record_shadow_intent(coordinator, spec)`（来源强制为 `shadow`）；替身环境另有 `POST /dev/shadow_intent` 便于验收。
这样模型 3 的 AI 先以影子档跑一段时间，所有意图都有完整留痕（含 `ai_eval_ref`），之后才可能提升到更高的执行档。

## 7. 与项目设计文档的对齐

意图 10 态沿用项目设计文档的命名；`ai_eval_ref` 对应其中「AI 评估引用」的接入位；幂等键、订单自定义编号（`DK<实例>-<模型>-<意图号 36 进制>-<分腿>`，见 `exchange/ids.py`）
与意图编号一一对应，崩溃重启后按编号回查、不重发。
